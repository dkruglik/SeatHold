Branch: `feature/phase-1-auth-access` · MR: not opened yet · Plan: `plans/phase_1_auth_access.plan.md` it-1 to it-8 · Date: 2026-11-26

Deploy order: Phase 0 first. This branch is built on the unmerged Phase 0 branch (`feature/phase-0-ignore-agent-env`, guide `phase-0-ignore-agent-env.md`). Merge and release Phase 0 before this one.

Placeholders used below: `<site-origin>` (the public https origin, the same value as `FRONTEND_ORIGIN`, for example the scheme and host without a path), `<test-email>` and `<admin-email>` (mailboxes you can read), `<database-url>` (the production `postgresql://` URL from the secret store), `<db-host>`, `<db-port>`, `<db-name>`, `<db-user>` (the production database connection details), `<secret-id>` (the secret holder in AWS Secrets Manager or SSM Parameter Store), `<generated-pepper>` and `<generated-csrf-secret>` (generated by the commands below). The README has no AWS commands and this repository holds no AWS names, so every AWS-specific step is marked `TODO(operator)`.

## What changes for users

Visitors can now sign in. They enter an email address, receive a six-digit code by email, and enter it. The code is valid for 10 minutes, allows 5 wrong attempts and works once. A first sign-in creates a `buyer` account. The session lasts 30 days (`SESSION_TTL_DAYS`) in the `sid` cookie. Logout ends it on the server.

Everything under `/api/admin/*` now requires an admin session: anonymous callers get 401, buyers get 403. There are no admin features yet; `GET /api/admin/ping` is a placeholder. Every state-changing browser request now needs the `X-CSRF-Token` header and an `Origin` equal to `FRONTEND_ORIGIN`. The frontend gets a login screen, a user menu and route guards, so the frontend must be released with the backend.

No admin exists after deploy. The seed is refused in production, so the first admin is created by hand (see "Before deploy", step 5).

Details: `README.md`, section "Authentication".

## Before deploy

1. Release Phase 0 first (see the header).
2. Generate the two secrets (each is at least 32 characters; these produce 64):

```bash
openssl rand -base64 48
openssl rand -base64 48
```

Use the first output as `AUTH_CODE_PEPPER` and the second as `CSRF_SECRET`. Do not reuse one value for both.

3. Put the secrets into the secret store (see "Environment variables"), and set the public variables on the production task environment.
4. Apply the migration (see "Migrations"). It must run before the new backend starts, because the backend does not create tables.
5. After the first deploy, the first admin is created later, in "After deploy", step 8. Nothing to do now.

### Environment variables

All variables are read by `backend/src/config/load-config.ts`. A wrong value stops the backend at startup with `Invalid configuration: <VARIABLE> ...`; the message names the variable and never prints its value.

Production rules enforced at startup:

- `EMAIL_PROVIDER=console` is refused.
- `COOKIE_SECURE` must be exactly `true`.
- `AUTH_CODE_PEPPER` and `CSRF_SECRET` must be at least 32 characters, and the local placeholders from `.env.example` are refused.
- `SMTP_USER` and `SMTP_PASS` are set together or not at all.
- `FRONTEND_ORIGIN` must be set, `https`, and not localhost (already required since Phase 0).

| Variable | Value for production | Where | Required | Notes |
|---|---|---|---|---|
| `EMAIL_PROVIDER` | `smtp` | production env | no (default `smtp`) | `smtp` or `console`. `console` is refused in production. |
| `EMAIL_FROM` | a sender address on a domain verified with the email provider | production env | no (default `no-reply@seathold.local`) | Must look like an email address. The default is a local placeholder and will not deliver in production. `TODO(operator)`: choose the sender address and verify its domain in SES. |
| `SMTP_HOST` | the SES SMTP endpoint of the production region | production env | no (default `localhost`) | The default only works with the local Mailpit. `TODO(operator)`: the SES SMTP host for the region. |
| `SMTP_PORT` | the SES SMTP port | production env | no (default `1025`) | Integer 1 to 65535. The default is the local Mailpit port. `TODO(operator)`: the SES SMTP port your network allows. |
| `SMTP_USER` | the SES SMTP user name | production env | yes in production, with `SMTP_PASS` | Not a secret on its own, but set together with `SMTP_PASS`. `TODO(operator)`: create SES SMTP credentials. |
| `SMTP_PASS` | the SES SMTP password | secret store (secrets block below) | yes in production, with `SMTP_USER` | Secret. Never in a file. |
| `AUTH_CODE_PEPPER` | generated (secrets block below) | secret store | yes | Secret. Keys the HMAC of login codes. Changing it invalidates every unused code only; sessions stay valid. |
| `CSRF_SECRET` | generated (secrets block below) | secret store | yes | Secret. Signs the CSRF cookie. Changing it makes existing CSRF cookies invalid; the frontend fetches a new token on its next mutation. |
| `AUTH_REQUEST_CODE_LIMIT` | `5` | production env | no (default `5`) | Positive integer: code requests per email in the window. |
| `AUTH_REQUEST_CODE_WINDOW_MINUTES` | `15` | production env | no (default `15`) | Positive integer. |
| `AUTH_REQUEST_CODE_COOLDOWN_SECONDS` | `60` | production env | no (default `60`) | Positive integer: minimum gap between two requests for one email. |
| `SESSION_TTL_DAYS` | `30` | production env | no (default `30`) | Positive integer. Fixed lifetime, no idle timeout. |
| `COOKIE_SECURE` | `true` | production env | yes in production (default `false`) | Adds `Secure` to the cookies. Production refuses anything but `true`. |

Already set by Phase 0 and unchanged: `APP_ENV=production`, `DATABASE_URL` (secret), `FRONTEND_ORIGIN` (`<site-origin>`), `DATABASE_POOL_MAX`, `LOG_LEVEL`, `SHUTDOWN_TIMEOUT_MS`, `BACKEND_HOST`, `BACKEND_PORT`. The backend now also reads `FRONTEND_ORIGIN` for the Origin check, so it must equal the exact browser origin, with no trailing slash and no path.

### Migrations

The backend deploy does not apply migrations (O35). This release adds one:

| Migration | What it does | Risk |
|---|---|---|
| `20261126120000_auth_schema` | Creates the `citext` extension (`CREATE EXTENSION IF NOT EXISTS citext`) and the tables `users`, `auth_codes` and `sessions`, their indexes, the foreign key `sessions.user_id` to `users.id` (delete cascade), and CHECK constraints on `users.role` (`buyer` or `admin`) and `auth_codes.attempts` (not negative). | Additive only. No existing table or data is touched, and no data is dropped. The tables are new and empty, so there are no long locks. The extension step needs the permission described next. |

Extension permission: `citext` is a trusted extension, so a role that owns the database (or has `CREATE` on it) can create it without being a superuser, on RDS and Aurora PostgreSQL 17. If the migration role lacks that permission, the migration fails at its first statement and nothing is applied.

Check it before migrating (read-only; replace nothing but the placeholders):

```bash
psql "host=<db-host> port=<db-port> dbname=<db-name> user=<db-user> sslmode=require" -c "SELECT name, trusted, installed_version FROM pg_available_extension_versions WHERE name = 'citext';"
```

Expected: one row with `trusted` `t` (`installed_version` is empty before the migration). If no row appears, the `citext` extension is not available on this server: stop and report it. If the next command fails with `permission denied to create extension "citext"`, create the extension once as the database owner:

```sql
CREATE EXTENSION IF NOT EXISTS citext;
```

Then run the migration again (it uses `IF NOT EXISTS`).

**Action:** apply the migration. It creates new tables only. Safe to repeat: Prisma records applied migrations in `_prisma_migrations` and skips them. Run it from a checkout of the release commit, with the database URL taken from the secret store (do not paste it into shared shell history or a file):

```bash
npm ci
export DATABASE_URL='<database-url>'
npm run db:migrate:deploy
unset DATABASE_URL
```

Expected: `1 migration found in prisma/migrations` (the only migration, `20261126120000_auth_schema`), then `All migrations have been successfully applied.`

`TODO(operator)`: run migrations against the direct database endpoint, not RDS Proxy (Prisma migrations take advisory locks and use session features that a proxy can pin or reject), unless you have tested the proxy path.

Check that it is applied:

```bash

npm exec -w backend -- prisma migrate status

```

Expected: `Database schema is up to date!`

## After deploy: check the feature

Set the shell variables once (placeholders from the header):

```bash
SITE='<site-origin>'
TEST_EMAIL='<test-email>'
JAR="$(mktemp)"
```

### 1. The backend started with the new configuration

```bash
curl -s "$SITE/api/health"
echo
```

Expected: `{"status":"ok"}`. If the tasks do not become healthy, read the task log: a line `Invalid configuration: <VARIABLE> ...` names the variable that is wrong or missing (`COOKIE_SECURE`, `EMAIL_PROVIDER`, `AUTH_CODE_PEPPER`, `CSRF_SECRET`, `SMTP_USER` or `SMTP_PASS`). Fix it and redeploy. `TODO(operator)`: the log-group name and the command to tail it (the README has no AWS commands).

### 2. An anonymous visitor is recognized and protected

```bash
curl -s "$SITE/api/auth/me"
echo
curl -s -o /dev/null -w '%{http_code}\n' "$SITE/api/admin/ping"
```

Expected: `{"user":null}`, then `401`.

### 3. A CSRF token is issued, and a mutation without it is refused

```bash
curl -s -c "$JAR" -b "$JAR" -H "Origin: $SITE" "$SITE/api/auth/csrf"
echo
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H "Origin: $SITE" -H 'Content-Type: application/json' -d "{\"email\":\"$TEST_EMAIL\"}" "$SITE/api/auth/request-code"
```

Expected: `{"csrfToken":"..."}` with a token value, then `403` (the second call has no token). A `403` is the code `CSRF_INVALID`. If the token request fails, check that `/api/*` is routed to the backend.

### 4. Request a login code (a real email is sent)

**Action:** sends one login email to `<test-email>` and writes one row to `auth_codes`. Safe: it only creates a code that expires in 10 minutes. The limit is 5 requests per 15 minutes per email, with 60 seconds between two.

```bash
CSRF_TOKEN="$(curl -s -c "$JAR" -b "$JAR" -H "Origin: $SITE" "$SITE/api/auth/csrf" | sed -n 's/.*"csrfToken":"\([^"]*\)".*/\1/p')"
curl -s -o /dev/null -w '%{http_code}\n' -c "$JAR" -b "$JAR" -X POST -H "Origin: $SITE" -H "X-CSRF-Token: $CSRF_TOKEN" -H 'Content-Type: application/json' -d "{\"email\":\"$TEST_EMAIL\"}" "$SITE/api/auth/request-code"
```

Expected: `204`. Then a message with a six-digit code arrives in the mailbox of `<test-email>` through the real SMTP provider, within about a minute. If the answer is `500` or `502`, the SMTP settings are wrong or the provider rejected the message: read the backend log for the error and check `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM` and the SES sender and sandbox state. If the answer is `429`, wait the number of seconds in the `Retry-After` header and retry. If the answer is `403`, check that `FRONTEND_ORIGIN` equals `<site-origin>` exactly.

### 5. Log in with the code

**Action:** verifies the code, creates the user `<test-email>` as a `buyer` if it does not exist, and creates one session. Safe: it adds one `users` row and one `sessions` row.

```bash
read -r -p 'Code from the email: ' CODE
curl -s -c "$JAR" -b "$JAR" -X POST -H "Origin: $SITE" -H "X-CSRF-Token: $CSRF_TOKEN" -H 'Content-Type: application/json' -d "{\"email\":\"$TEST_EMAIL\",\"code\":\"$CODE\"}" "$SITE/api/auth/verify"
echo
```

Expected: a body with `"user"` and `"role":"buyer"` (for a new account). The cookie jar now holds `sid` with the `Secure` and `HttpOnly` attributes:

```bash
grep -E 'sid|csrf_secret' "$JAR" | awk '{print $1, $6}'
```

Expected: two lines with the cookie names `sid` and `csrf_secret` (the host and its `#HttpOnly_` prefix appear in the first column). A wrong code gives `400` with the code `INVALID_CODE` and no cookie.

### 6. The session works

```bash
curl -s -b "$JAR" "$SITE/api/auth/me"
echo
```

Expected: `{"user":{...}}` with the same account.

### 7. A buyer cannot reach the admin area

```bash
curl -s -o /dev/null -w '%{http_code}\n' -b "$JAR" "$SITE/api/admin/ping"
```

Expected: `403` (code `FORBIDDEN_ROLE`). If it prints `200`, stop: access control is broken. Roll back (see "Rollback") and report it.

### 8. Create the first admin

**Action:** changes the role of one existing user to `admin`. Safe: it changes one `users` row, only for an address that has already signed in once, and `npm run user:demote -- <admin-email>` reverses it. No admin email exists in advance because the seed is refused in production.

Prerequisite: the person who will be admin has signed in once (steps 4 and 5, or through the site). If the address is not known, the command prints a message and exits 1; no user is created.

Run it from a checkout of the release commit with the production environment (it reads `DATABASE_URL`; the other variables come from `loadConfig`, so set the same values the backend has, or at least the required ones):

```bash
npm ci
export DATABASE_URL='<database-url>'
export AUTH_CODE_PEPPER='<generated-pepper>'
export CSRF_SECRET='<generated-csrf-secret>'
export APP_ENV=production
export FRONTEND_ORIGIN='<site-origin>'
export COOKIE_SECURE=true
export EMAIL_PROVIDER=smtp
npm run user:promote -- '<admin-email>'
unset DATABASE_URL AUTH_CODE_PEPPER CSRF_SECRET
```

Expected: `<admin-email> is now admin` (or `already admin` when repeated). Exit code 0. `TODO(operator)`: run this from a one-off task in the production network instead of a checkout if the database is not reachable from where you run it.

Check the effect without logging in again (the role is read on every request): sign in as that admin as in steps 4 and 5 with `TEST_EMAIL` set to `<admin-email>` and a new `JAR`, then:

```bash
curl -s -b "$JAR" "$SITE/api/admin/ping"
echo
```

Expected: `{"ok":true}`.

### 9. Log out

**Action:** revokes the current session on the server. Safe: it ends only this test session.

```bash
CSRF_TOKEN="$(curl -s -c "$JAR" -b "$JAR" -H "Origin: $SITE" "$SITE/api/auth/csrf" | sed -n 's/.*"csrfToken":"\([^"]*\)".*/\1/p')"
curl -s -o /dev/null -w '%{http_code}\n' -c "$JAR" -b "$JAR" -X POST -H "Origin: $SITE" -H "X-CSRF-Token: $CSRF_TOKEN" "$SITE/api/auth/logout"
curl -s -b "$JAR" "$SITE/api/auth/me"
echo
rm -f "$JAR"
```

Expected: `204`, then `{"user":null}`.

### 10. The browser flow

Open `<site-origin>`, sign in with the email code, check that the user menu shows the account, that `/admin` shows the not-allowed page for a buyer and the admin page for an admin, and that logout returns to the signed-out state. This has not been exercised in a real browser against a real backend (DECISIONS.md O56).

### SQL checks

Open psql (read-only queries; they return counts and no emails or tokens):

```bash
psql "host=<db-host> port=<db-port> dbname=<db-name> user=<db-user> sslmode=require"
```

```sql
-- The three tables and the citext extension exist; expected: 4 rows (auth_codes, sessions, users, then citext)
SELECT table_name AS name FROM information_schema.tables WHERE table_schema = 'public' AND table_name IN ('users', 'auth_codes', 'sessions')
UNION ALL
SELECT extname FROM pg_extension WHERE extname = 'citext'
ORDER BY name;

-- Accounts by role; expected: the buyers who signed in plus exactly the admins you promoted (at least 1 admin after step 8)
SELECT role, count(*) AS users FROM users GROUP BY role ORDER BY role;

-- Sessions; expected: active equals the people currently signed in, revoked grows with logouts
SELECT count(*) FILTER (WHERE revoked_at IS NULL AND expires_at > now()) AS active,
       count(*) FILTER (WHERE revoked_at IS NOT NULL) AS revoked,
       count(*) FILTER (WHERE revoked_at IS NULL AND expires_at <= now()) AS expired
FROM sessions;

-- Login codes; expected: used + invalidated + unused = total, and unused codes older than 10 minutes are expired
SELECT count(*) AS total,
       count(*) FILTER (WHERE consumed_at IS NOT NULL) AS used,
       count(*) FILTER (WHERE invalidated_at IS NOT NULL) AS invalidated,
       count(*) FILTER (WHERE consumed_at IS NULL AND invalidated_at IS NULL AND expires_at > now()) AS usable
FROM auth_codes;

-- No admin without a deliberate promotion; expected: the count you promoted (compare with step 8)
SELECT count(*) AS admins FROM users WHERE role = 'admin';

-- The migration is recorded; expected: 1 row, finished_at not null, rolled_back_at null
SELECT migration_name, finished_at IS NOT NULL AS finished, rolled_back_at IS NOT NULL AS rolled_back
FROM _prisma_migrations WHERE migration_name = '20261126120000_auth_schema';
```

Note: `auth_codes` is never purged in this release; rows accumulate (see "Known limits").

## Rollback

The migration is additive, so it is safe to keep when the application is rolled back: the previous release ignores the three tables.

Application rollback: redeploy the previous backend image and frontend build, and remove or leave the new variables (the previous release ignores them). Sessions are lost on rollback: the previous release has no login, so nobody is signed in. If you keep the tables, unexpired sessions and admin roles become valid again when you roll forward. If you drop the tables (below), everyone signs in again and the admin must be promoted again.

To also undo the schema (only if nothing needs the data; this deletes all accounts, sessions and login codes and cannot be undone):

**Action:** drops the three auth tables and removes the migration record. Run it only after the application rollback, so no instance writes to the tables meanwhile.

```sql
BEGIN;
DROP TABLE IF EXISTS "sessions";
DROP TABLE IF EXISTS "auth_codes";
DROP TABLE IF EXISTS "users";
DELETE FROM "_prisma_migrations" WHERE migration_name = '20261126120000_auth_schema';
COMMIT;
```

Expected: `COMMIT`. The `citext` extension is left in place; it is harmless. Drop it with `DROP EXTENSION IF EXISTS citext;` only if you are sure nothing else uses it.

If login is the only problem and the rest of the site must stay up, there is no switch to turn auth off: roll back the application.

## Known limits

- The backend image has no migration path (DECISIONS.md O35 stays `planned`): the operator applies migrations by hand until a one-off task exists.
- The login flow, the SMTP adapter against SES and the frontend guards have not been exercised against a real provider or a real browser, and the GitHub Actions workflow has not run (DECISIONS.md O56).
- Not built yet, recommended before production (O56): AWS WAF rate rules, an idle timeout for admin sessions, an admin audit log, a fresh code before destructive admin actions, and a purge job for old `auth_codes` rows. Until then the table grows with every request.
- The request limit and the attempt count can overshoot by the number of concurrent requests (O43). The CSRF secret and token are not bound to the user and are not rotated on login (O46).
- Creating the seeded admin is two statements; the seed is not used in production. If a promotion is interrupted, `npm run user:promote -- <admin-email>` repairs it (O51).
